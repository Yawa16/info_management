# Hope, Inc. ERP

Next.js App Router app for the Hope, Inc. business management system.

For the cross-platform, no-Docker team database workflow, follow the
[student database setup guide](db/README.md). It covers the Supabase PostgreSQL
connection, migrations and seeds, verification, reset safeguards, and team
migration rules. Apply application migrations only to the team-approved
development project after confirmation from the DB Admin.

## Local setup

1. Install dependencies:

   ```powershell
   npm ci
   ```

2. Copy `.env.local.example` to `.env.local` and fill in the local Supabase
   settings. If Next.js uses a different port, set `NEXT_PUBLIC_SITE_URL` to
   the exact local origin it prints. Keep `.env.local` out of Git.

3. Apply `supabase/migrations/20261025100000_health_check.sql` only to the
   approved development project. This migration adds a read-only health-check
   RPC; `/api/health` returns `{"status":"ok","database":"connected"}` when the
   connection works.

4. Start the development server:

   ```powershell
   npm run dev
   ```

   The development server is pinned to port `3000`; if that port is occupied,
   the command exits instead of silently switching ports. Visit
   `http://localhost:3000` for the landing page and
   `http://localhost:3000/api/health` to check Supabase connectivity.

Use `npm run typecheck` and `npm run build` to verify the project.

## Customer list

The `/customers` page requires the DB Admin's `public.customer` schema with
`cust_no`, `cust_name`, `address`, `pay_terms`, `status`, and `stamp` columns.
`status` must contain `Active` or `Inactive`. Check the target project with
the DB Admin before applying or changing database migrations. Search and status
filters run in the database; tab counts reflect the current search. The list
is paginated at 50 rows.

For the legacy Customer schema, `db/migrations/20261117233000_customer_status_compatibility.sql`
renames the Customer columns and maintains both `status` and the existing
`is_deleted` flag for legacy triggers. It enables RLS with no direct-client
policies; the page accesses the table through its authorized server. The
manually applied migration is recorded in `public.schema_migrations` on the
shared project. Its `applied_at` is the reconciliation time, not the original
application time. Do not run it there a second time.
`db/migrations/20261118002000_normalize_customer_legacy_stamps.sql` converted
legacy `ADD` stamps while preserving the original actor and time, recording
each formatting change in the audit log; it is also recorded as applied.
The inactive C-004 test customer was added separately and is not part of the
migration.

Run the focused query tests with Node.js 24:

```powershell
node --test tests\customer-list.test.mjs
```

### Customer create and edit

The Add and Edit dialogs validate input and check the corresponding Customer
right on the server. Customer numbers, status, and stamps are generated by the
database. The server-only RPC records the authenticated user's ID in the stamp
and audit log; inactive customers cannot be edited.

The DB Admin must review and apply
`db/migrations/20261118040000_customer_create_edit.sql` to the approved target
before saving customers. It was applied and recorded in migration history on
the shared project. It widens legacy Customer fields and the Sales customer
reference, retains legacy pay terms, and makes the legacy Customer view obey
the caller's RLS policies. Its SQL execution log is in
`supabase/reviews/s2-dev-02-sql-execution-log.sql`. Run
`supabase/tests/customer_form.sql` on an approved test database after applying
the migration; it rolls back its changes. Run focused application tests with
`node --test tests\customer-actions.test.mjs tests\customer-form.test.mjs tests\customer-list.test.mjs`.

### Customer delete and restore

Delete is a confirmed soft delete. The server checks the Delete Customer right;
only Admins and Superadmins may restore. Regular Users see active rows only,
while managers can find shaded inactive rows using the status filters. Existing
database rules prevent deleting customers with active sales and report this
restriction to the user. Database triggers preserve the row, update its status
and stamp, and record the authenticated actor in the audit log.

The DB Admin must review and apply
`db/migrations/20261118050000_customer_delete_restore.sql` to an approved
database before using these actions. It was applied and recorded in migration
history on the shared project. The SQL execution log is in
`supabase/reviews/s2-dev-03-sql-execution-log.sql`. Run
`supabase/tests/customer_delete_restore.sql` on an approved test database after
applying the migration; the test rolls back all changes.

## Product list

The `/products` page follows the Customer list pattern: Prod Code, Description,
Unit, and Current Price (shown as "—" until the price tasks). Admins and
Superadmins also see Status, Stamp, Active / Inactive / All tabs with counts,
and shaded inactive rows. Users see only Active products, with no Status or
Stamp; this is enforced in the server query, not only in the UI. Search runs in
the database as you type. The Prices button is a disabled placeholder.

The legacy Product table uses `prodcode` and `is_deleted` and has RLS off.
`db/migrations/20261118060000_product_status_compatibility.sql` renames the
column to `prod_code`, adds `status` kept in sync with `is_deleted`, replaces
the Product delete guard and audit trigger, enables RLS with no direct-client
policies, and recreates `product_active` with `security_invoker` so it obeys
RLS. `db/migrations/20261118061000_normalize_product_legacy_stamps.sql`
rewrites legacy `ADD` stamps to `CREATED`, keeping the original actor and time
and auditing each change. Both migrations have been reviewed and recorded on
the shared project as `20261118060000_product_status_compatibility.sql` and
`20261118061000_normalize_product_legacy_stamps.sql`; do not rerun them there.
Run `supabase/tests/product_list.sql` on an approved test database after
applying them; it rolls back its changes. Run the focused tests with
`npm run test:products`.

## Product create

Users with `PRODUCT_ADD` can open the Add Product modal. Description and Unit
are required, Unit accepts descriptive values such as `pcs`, `can`, `pair`, or
`meter`, and no price field is included. The application calls the
service-role-only `save_product_form` RPC, which generates `P-001`, `P-002`,
and later codes; direct anonymous or authenticated RPC calls are denied.

`db/migrations/20261122080000_product_create_form.sql` is prepared but must be
reviewed and applied by the DB Admin to an approved database. It widens
Description and Unit, removes the legacy unit whitelist, and adds the create
RPC. Do not rerun migrations already recorded in `public.schema_migrations`.

## Supabase scaffold

The reusable Supabase clients are in `lib/supabase/client.ts` for browser
components and `lib/supabase/server.ts` for server components, actions, and
route handlers. Both use the project URL and anon key; the service-role client
is separate and server-only.

The health-check migration does not create application tables or verify their
schema. Keep `.env.local` private; never put a service-role key in a
`NEXT_PUBLIC_` variable.

## Registration setup

Copy `.env.local.example` to `.env.local` and set the Supabase project URL,
anon key, local site URL, and server-only service-role key. Set the site URL to
the exact local origin printed by `npm run dev`, including its port. Never
expose or commit the service-role key; it bypasses RLS and is used only by
server-side registration and profile approval checks.

The migration `supabase/migrations/20261028170000_create_profiles_table.sql`
defines `public.profiles` with the following schema:

| Column | Expected type / behavior |
| --- | --- |
| `id` | `uuid`, primary key and foreign key to `auth.users.id` |
| `first_name` | `text`, required, 1–80 trimmed characters |
| `last_name` | `text`, required, 1–80 trimmed characters |
| `email` | `text`, required and unique |
| `role` | `text`, one of `superadmin`, `admin`, or `user`; defaults to `user` |
| `approval_status` | `text`; new accounts are `pending`, and approved accounts are `active` (legacy `approved` rows remain accepted) |
| `created_at` | `timestamptz`, defaults to the current time |

The migration enables RLS, permits authenticated users to read only their own
profile, and grants no client-side insert, update, or delete access. Server
actions use the server-only service-role key and must perform their own
authorization checks. The registration action always assigns
`role = 'user'` and `approval_status = 'pending'` on the server; it ignores any
role or approval values supplied by a browser.

The `/api/health` endpoint calls the Supabase RPC `public.health_check()`. A
successful response is `{"status":"ok","database":"connected"}`. This checks
connectivity to the project configured in `.env.local`; it does not verify the
profiles schema.

Before applying the migration, have the DB Admin confirm the intended schema
and target project. The project shown in the earlier screenshots is marked
Production and already contains an `app_user` table, so do not apply this
migration there or create duplicate user data without explicit approval.

Registration asks only for first name, last name, and email. The server creates
a cryptographically random initial Supabase Auth password, which is never
shown or stored by the application, and creates a pending regular User profile
with `must_change_password = true`. If email confirmation is enabled, the user
must follow the confirmation link first. The authenticated user then remains on
`/approval-pending`, which checks approval status and opens `/set-password`
after a Superadmin approves the account. After setting a password, the user is
signed out and must sign in with their email and new password.

Authentication and email-confirmation links return through `/auth/callback`.
In the development Supabase project's Authentication → URL Configuration, set
the Site URL to the local origin and allow the callback URLs, for example
`http://localhost:3000/auth/callback`,
`http://localhost:3000/auth/callback?flow=email-registration`,
`http://localhost:3000/auth/callback?flow=managed-registration`,
`http://localhost:3000/auth/callback?flow=registration`, and
`http://localhost:3000/auth/callback?flow=recovery&next=/reset-password/update`.
Password reset links return to `/reset-password/update`; after a successful
password change, the user is signed out and must sign in again. Expired or
invalid recovery links return to `/reset-password`, where the user can request
a new link. Do not change production Supabase settings for local testing.

Password reset email delivery uses Supabase Auth's Reset Password email
template and configured SMTP provider. Keep `{{ .ConfirmationURL }}` in the
template so Supabase validates the one-time token before redirecting to the
app callback. Configure SMTP under Authentication → SMTP Settings in the
development project; Supabase's default email service is rate-limited and
restricted to authorized project-team addresses. Use an authorized sender
domain for messages to other addresses, and never put SMTP credentials in the
app or commit them.

The registration and sign-in pages also support Google OAuth. Configure Google as an
enabled provider under the development project's Authentication → Providers
settings, including the Google OAuth client ID and secret. Copy the Supabase
provider callback URL into the Google OAuth client's authorized redirect URIs,
and allow the development app's `/auth/callback` URL in Supabase's redirect
URL settings. First-time Google sign-ups create regular User profiles with
pending approval; they do not grant access until an Admin or Superadmin
approves the account. Approved accounts are directed to `/set-password` before
they can enter the ERP.

The login flow checks the profile on the server and rejects users whose
approval status is pending or rejected. Only Superadmins can approve or
reject pending regular User accounts in `/users`; approval changes the status
to `active` and requires first-time password setup. The server verifies the
caller's authenticated profile and only
updates a target row whose role is `user` and status is `pending`; Admins
cannot view or modify Superadmin accounts. Protected pages must be placed under
`app/(protected)/` so its server layout checks the current Supabase user and
approval status on every request. Server actions and route handlers that
access protected data must also check approval status before doing work; the
layout is not a substitute for authorization in data operations.

The registration action always sets `role = 'user'` and
`approval_status = 'pending'` on the server and never accepts those values
from the browser. Confirm with the DB Admin that the status used after
approval is exactly `active` before deploying this check. Existing `approved`
profiles remain accepted for compatibility.

## Login and first-time password setup

The migration `supabase/migrations/20261101100000_add_login_access_flags.sql`
adds `must_change_password` and `is_blocked` boolean columns to
`public.profiles`. Both default to `false`. Apply it to the approved Supabase
project before deploying the Task 3 login code. The Task 5 migration keeps
profiles RLS enabled and adds role-scoped policies for User Management.

Login uses Supabase Auth, which stores password hashes; the application never
hashes or stores passwords itself. After authentication, the server checks the
profile. Pending, rejected, and blocked accounts are signed out and shown an appropriate
message. Active accounts with `must_change_password = true` are redirected
to `/set-password` while signed in. After the password is changed, the server
clears that profile flag. Forgot Password remains a separate email-reset flow.
Admin-created temporary accounts must have this flag set to `true` by the
trusted server-side account creation flow. The `/users` page provides an
Admin/Superadmin-only form to create regular User accounts with temporary
passwords; it creates the Auth user and active profile server-side and
requires a password change at first sign-in.

Middleware refreshes Supabase cookies so sessions survive navigation and
refreshes. Protected pages verify the session and profile server-side on every
request. Repeated failed sign-in attempts rely on Supabase Auth's configured
rate limits; review the Auth rate-limit settings in the Supabase project.

## Task 5: User Management

The `/users` page is available only to approved, unblocked Admins and
Superadmins. Admins see regular User and Admin accounts, but can manage only
regular Users; Superadmin accounts are omitted. Superadmins can manage other
accounts of every role. Neither role can manage its own account. The Rights
control is intentionally disabled as a placeholder for a later task.

The page supports creating a regular, active User with a cryptographically
random temporary password, editing account name/email, and blocking or
unblocking accounts. The generated password is shown after successful
creation so it can be shared privately. New managed accounts set
`must_change_password = true` and must visit `/set-password` before reaching
protected pages. Blocking is confirmed in the browser; the server also
validates the caller and target on every action. Existing login and protected
page checks reject blocked accounts.

Apply `supabase/migrations/20261104133000_user_management.sql` only to the
approved development Supabase project after confirmation from the DB Admin.
The migration keeps RLS enabled, adds manager-scoped profile read/update
policies, and limits authenticated profile updates to the name, email, and
block-status columns. The server actions independently enforce the same role
and self-management rules. Auth account creation and email changes use the
server-only service-role client; passwords remain managed by Supabase Auth.

The SQL migration is committed but has not been applied to any Supabase
project. Verify against the approved development project before deployment;
do not apply it to production without explicit approval.

## Task 6: Superadmin controls and last-Superadmin protection

The Superadmin-only Pending approvals section on `/users` lists pending
regular User registrations with Approve and Reject actions. Admins and regular
Users do not see the section and cannot invoke its actions.
Approve sets `approval_status = 'active'` and requires first-time password
setup. Reject sets `approval_status = 'rejected'`; it keeps the Auth/profile
records for auditability, but rejected profiles cannot sign in to protected
ERP pages.
The Superadmin can also promote an active User to Admin or demote an active
Admin to User in User Management. Every action re-reads the authenticated
caller and target on the server; Admins cannot invoke these actions.

Before blocking an active Superadmin, the server checks that another active,
unblocked Superadmin remains. The Task 6 database migration adds a
`BEFORE UPDATE OF role, approval_status, is_blocked OR DELETE` trigger that
repeats this invariant inside the database, serializes competing
demotion/block/delete attempts with a
transaction-scoped advisory lock, and raises a clear error if an action would
remove the last active Superadmin. This also protects deletes through the
`auth.users` foreign-key cascade. RLS stays enabled; the existing manager
update policy limits role updates to Superadmins and regular User targets for
Admins, and authenticated clients are not granted direct updates to
`approval_status`.

The DB Admin should apply
`supabase/migrations/20261104210000_task6_superadmin_controls.sql` only to
the approved development project after reviewing it. Confirm whether the DB
Admin has already applied this exact version. The migration extends
the status constraint for `active` and `rejected`, refreshes the Task 5 RLS
authorization functions to accept active Superadmins/Admins, and installs the
last-Superadmin trigger.
