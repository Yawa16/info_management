Authentication wireframes

Task 2 · Mid-fidelity · Responsive samples at 1440px, 768px, and 375px. Shared card, field order, and vertical rhythm across all auth routes.

Assumptions and Task 1 reuse

Production request creates an Inactive User; Admin approval is required before login. Existing DEV instruction defaults signups to Superadmin, a documented conflict.

Roles/statuses: Superadmin, Admin, User; Active, Inactive, Blocked. New-password policy is 12+ characters with upper, lower, number, symbol.

One-time invite/reset links are assumed to expire after 60 minutes. Login locks for 15 minutes after 5 failed attempts; reset resend cooldown is 60 seconds.

Uses Task 1 cream, border, surface, text, focus, primary, success, and danger tokens; Inter; documented button, input, password, inline error, and card patterns.

These timing and password-policy values are provisional. Confirm them with product/security before implementation. Auth-specific summary, checklist, cooldown, and token-recovery patterns were not defined in Task 1.

Flow overview

Login→ Forgot password →Request reset→Check email→Choose new password→ Login
Register→Submitted→ Admin approval →Set password→ Login
Login errors: validation / generic credentials / Inactive / Blocked / temporary lockout / expired session
Register errors: validation / email already used / passwords mismatch / registration closed
Set/reset link expired or invalid/used → request/reissue link → retry

Contact administrator route

Use your organization's configured administrator/support channel. The actual destination must be supplied by the product owner.
