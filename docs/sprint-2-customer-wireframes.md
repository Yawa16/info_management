# Hope, Inc. ERP — Sprint 2 Customer Wireframes

**Ticket:** S2-UIX-01 · **Module:** Customers · **Reference viewport:** 1440px

## 1. Scope and assumptions

This handoff specifies the customer list/search, add, edit, soft-delete, restore,
and permission variants. It reuses the Sprint 1 tokens and components in the
[Hope ERP design system](./hope-erp-design-system.md) and
[style guide](./hope-erp-style-guide.html); it introduces no colors, sizes, or
components.

| Topic | Assumption for implementation |
|---|---|
| Customer number | Generated by the system on creation; show it as read-only after saving and on edit. Do not ask the user to invent a number. |
| Required fields | Customer Name and Pay Terms are required; Address is optional. |
| Status terms | Use `Active` and `Inactive` in the Status column and tabs. Inactive is a soft-deleted record; its latest stamp uses `DELETED`. |
| Rights | A control is shown only when the signed-in user has the matching right. Restore is included in `Delete Customer`; users without it cannot restore. |
| Role visibility | User-role accounts see active records only, even when granted a delete right. Admin and Superadmin accounts can view all statuses. Role alone does not grant an action right. |
| Counts | Status-tab counts are totals for each status and do not change with the search query. The result count reflects the selected status and current search. |
| Search | Match Cust No, Customer Name, Address, and Pay Terms; ignore letter case and surrounding spaces. A cleared query returns to the selected status's full list. |
| Blocked delete | The server provides the active-sales count and remains authoritative. The UI does not offer a bypass. |
| Restore audit | Because the defined stamp events are CREATED / EDITED / DELETED and no RESTORED event is specified, record a successful restore as an EDITED event. |

Example audit identities and dates below are placeholders, not actual customer
history. Use the viewer's locale and timezone for real stamps.

## 2. Shared desktop frame

| Region | Specification |
|---|---|
| App shell | Sprint 1 expanded sidebar, 256px wide; active Customers navigation item with `aria-current="page"`. |
| Main content | Warm page canvas; 32px desktop gutters; content max-width 1200px. At 1440px, the sidebar leaves 1184px for content, so the usable centered content width is 1120px. |
| Page heading | `Customers` (28/36, semibold); supporting text: `Manage customer records and payment terms.` |
| Surfaces and controls | Use the existing surface, border, shadow, button, input, table, badge, dialog, and alert tokens/components as specified in the design system. |
| Focus and keyboard | All controls are keyboard-operable. Show the 2px `--color-focus` outline with 2px offset. Use semantic headings/table markup and persistent labels. |
| Feedback | Keep validation and blocking errors next to the relevant field/action. Announce results and save/delete/restore outcomes; do not rely on color alone. |

## 3. Customer list and search

### Wireframe: Admin / Superadmin

```text
┌──────────────────────────────────────────────────────────────────────────┐
│ Customers                                            [+ Add customer]    │
│ Manage customer records and payment terms.                               │
│                                                                          │
│ [ Active 4 ] [ Inactive 1 ] [ All 5* ] [ Search customers...       × ]  │
│ Showing 5 customers                                                      │
│ ┌──────────┬─────────────────────┬───────────────┬──────────┬──────────┐ │
│ │ Cust No  │ Customer Name       │ Address       │ Pay Terms│ Status   │ │
│ ├──────────┼─────────────────────┼───────────────┼──────────┼──────────┤ │
│ │ C-001    │ Acme Corporation     │ —             │ Net 30   │ Active   │ │
│ │          │ CREATED · [user] · [date/time]                     actions│ │
│ │ C-002    │ Globex Industries    │ —             │ Net 45   │ Active   │ │
│ │          │ EDITED · [user] · [date/time]                      actions│ │
│ │ C-003    │ Initech LLC          │ —             │ COD      │ Active   │ │
│ │          │ CREATED · [user] · [date/time]                     actions│ │
│ │ C-004    │ Umbrella Corp        │ —             │ Prepaid  │ Inactive │ │
│ │          │ DELETED · [user] · [date/time]               [Restore]   │ │
│ │ C-005    │ Stark Enterprises    │ —             │ Net 15   │ Active   │ │
│ └──────────┴─────────────────────┴───────────────┴──────────┴──────────┘ │
└──────────────────────────────────────────────────────────────────────────┘
```

`*` marks the selected status tab in the example.

In the finished table, split the audit stamp and Status into their own columns;
the compact wireframe places the stamp beneath the customer name only to keep
the example legible. The implemented Admin/Superadmin column order and
behavior are:

| Order | Column | Content and behavior |
|---:|---|---|
| 1 | Cust No | Customer number, e.g. `C-001`. |
| 2 | Customer Name | Customer name only. |
| 3 | Address | Full address; show an em dash when absent. |
| 4 | Pay Terms | Payment term label. |
| 5 | Status | Text badge `Active` or `Inactive`; icon/label as well as color. |
| 6 | Stamp | Latest `CREATED`, `EDITED`, or `DELETED` event, actor, and localized date/time. Use the exact Sprint 1 pattern: `VERB · {user} · {date}`. |
| 7 | Actions | Authorized actions only. Active rows may show Edit and Delete. Inactive rows show Restore instead of Edit/Delete. Omit the Actions column when the viewer has no action rights for any displayed row. |

### Wireframe: User role

```text
┌──────────────────────────────────────────────────────────────────────────┐
│ Customers                                            [+ Add customer]    │
│ Manage customer records and payment terms.                               │
│                                                                          │
│ [ Search customers...                                               × ]  │
│ Showing 4 customers                                                      │
│ ┌──────────┬─────────────────────┬────────────────┬──────────┬─────────┐ │
│ │ Cust No  │ Customer Name       │ Address        │ Pay Terms│ Actions │ │
│ ├──────────┼─────────────────────┼────────────────┼──────────┼─────────┤ │
│ │ C-001    │ Acme Corporation     │ —              │ Net 30   │ Edit    │ │
│ │ C-002    │ Globex Industries    │ —              │ Net 45   │ Edit    │ │
│ │ C-003    │ Initech LLC          │ —              │ COD      │ Edit    │ │
│ │ C-005    │ Stark Enterprises    │ —              │ Net 15   │ Edit    │ │
│ └──────────┴─────────────────────┴────────────────┴──────────┴─────────┘ │
└──────────────────────────────────────────────────────────────────────────┘
```

| Element | User-role behavior |
|---|---|
| Rows and columns | Active rows only. Show Cust No, Customer Name, Address, and Pay Terms. Never show Status or Stamp. |
| Search | Search only the active rows. Show a result count and an explicit no-results state. |
| Add | Show `+ Add customer` only with `Add Customer`. |
| Edit | Show Edit only on active rows and only with `Edit Customer`. |
| Delete | Show Delete only on active rows and only with `Delete Customer`. Deleting an active row removes it from this role's active-only list; restoration is available to an authorized Admin/Superadmin. |
| Status filters / Restore | Do not show tabs, inactive records, or Restore to User-role accounts. |

### List and search details

| Item | Specification |
|---|---|
| Toolbar | Admin/Superadmin: status tabs on the left, search on the right; wrap when necessary. User: search only. Place the Add button at the page-heading level. |
| Status tabs | Admin/Superadmin only: `Active {count}`, `Inactive {count}`, `All {count}`. Default to Active. Selected state is visibly outlined and programmatically exposed (`aria-selected`). |
| Search field | Persistent accessible name `Search customers`; placeholder `Customer number, name, address, or payment terms`. Provide a keyboard-accessible clear control with name `Clear search`. Keep the selected status when searching. |
| Result count | Announce the number of matching rows after search/filter changes (e.g. `Showing 1 of 4 active customers`). |
| Sort | Default Cust No ascending. If sorting is offered, indicate direction and `aria-sort`; do not use color alone. |
| Table | Semantic header cells with `scope="col"`. Keep readable text at 12px minimum; use horizontal scrolling rather than compressing columns. Keep row actions available without hover. |
| Deleted rows | Use `--color-row-deleted` and readable text, with the explicit `Inactive` label and DELETED stamp. Shading is supplemental, never the only status cue. |

| State | Display |
|---|---|
| Loading | Table-shaped loading state with an announced `Loading customers` message. |
| No records | `No customers yet.` Show the Add action only if the viewer has `Add Customer`. |
| No search results | `No customers match “[query]”.` Provide `Clear search`; preserve the selected status. |
| List error | Persistent alert: `Customers couldn't be loaded. Try again.` Include a keyboard-accessible Retry action. Do not display a successful empty state. |

## 4. Add and edit customer

Both use the existing Sprint 1 form-dialog pattern: accessible title, 430px
maximum width, surface with dialog shadow, and sticky footer. On mobile the
dialog uses near-full-screen width. Move focus into the dialog, contain Tab
navigation, close on Escape when safe, and return focus to the opener.

│ Edit customer                         [Close]│

| Field / control | Add | Edit | Validation and accessibility |
|---|---|---|---|
| Customer No | Not entered; system-generated on successful creation. | Read-only value. | Do not make a generated identifier appear editable. |
| Customer Name | Empty text input. | Current value. | Required; trim surrounding whitespace. Inline error: `Enter a customer name.` |
| Address | Empty text input. | Current value. | Optional. Preserve entered line breaks if multiline input is used. |
| Pay Terms | Native/single select, initially `Select payment terms`. | Current value selected. | Required; only `Net 15`, `Net 30`, `Net 45`, `COD`, `Prepaid`. Inline error: `Select payment terms.` |
| Cancel / close | Discard and close; if dirty, confirm before discarding. | Discard and close; if dirty, confirm before discarding. | Cancel is secondary; close has accessible name. Return focus to the triggering control. |
| Save | Create customer. | Save edits. | Disable only while invalid/submitting as appropriate; retain values on error. Loading label `Saving…`; prevent duplicate submission. |

Validation errors stay beside and are programmatically associated with their
fields using `aria-describedby` and `aria-invalid`. On submit, focus the first
invalid field. On success, close the dialog, announce `Customer added.` or
`Customer updated.`, and refresh the list. Update the audit stamp on successful
edit; do not let the user type or choose a stamp.

| Permission | Add dialog | Edit dialog |
|---|---|---|
| `Add Customer` absent | Hide the Add button; do not open the dialog. | No effect on Edit. |
| `Edit Customer` absent | No effect on Add. | Hide Edit actions; do not open the dialog. |
| Server rejects save | Keep the dialog and entered values. Show an actionable inline/global error; do not announce success. | Keep the dialog and entered values. Show an actionable inline/global error; do not announce success. |

## 5. Soft delete

Delete is a reversible soft-delete action, not permanent erasure. It moves the
customer to Inactive, records a `DELETED` stamp, and makes Restore available to
authorized Admin/Superadmin accounts.

### Confirmation when deletion is allowed

```text
┌──────────────────────────────────────────────┐
│ Delete customer?                      [Close]│
│ Delete Acme Corporation (C-001)?             │
│ The customer will become inactive and can   │
│ be restored by an authorized administrator. │
├──────────────────────────────────────────────┤
│                         [Cancel] [Delete]    │
└──────────────────────────────────────────────┘
```

| Behavior | Specification |
|---|---|
| Entry point | Show Delete only on an active row when the viewer has `Delete Customer`. |
| Confirmation | Name both customer and number. Explain soft deletion and restoration. Use Cancel and explicit danger action `Delete customer`; do not use a generic Confirm label. |
| Success | Close, announce `Customer moved to Inactive.`, and refresh the list. In an Active view the row disappears; in All it remains shaded and labeled Inactive. |
| Failure | Keep context and show a persistent actionable error. Do not report a successful deletion or silently update the row. |
| Permission denied | Hide the control. The server independently checks `Delete Customer` for every request. |

### Deletion blocked by active sales

```text
┌──────────────────────────────────────────────┐
│ Customer can't be deleted             [Close]│
│ Acme Corporation (C-001) has 3 active sales. │
│ Close or cancel those sales before deleting  │
│ this customer.                               │
├──────────────────────────────────────────────┤
│                                      [Close] │
└──────────────────────────────────────────────┘
```

| Rule | Specification |
|---|---|
| Count | Show the exact active-sales count returned by the server, including singular/plural wording (e.g. `1 active sale`, `3 active sales`). |
| Action | No Delete/confirm action is offered while blocked. Provide Close only; do not suggest the record is inactive or deleted. |
| Variants | When a user has delete permission and deletion is blocked, explain the same count and reason. If permission is missing, hide Delete and do not expose the blocker through a hidden action. |
| Stale data / race | If the server rejects an attempted deletion because active sales exist, keep the record active and display the server's current count. |

## 6. Restore

Restore is available for an Inactive row to Admin/Superadmin accounts with
`Delete Customer`. User-role accounts never see inactive rows or Restore.

```text
┌──────────────────────────────────────────────┐
│ Restore customer?                     [Close]│
│ Restore Umbrella Corp (C-004) to Active?     │
│ It will appear in active customer lists.     │
├──────────────────────────────────────────────┤
│                          [Cancel] [Restore]  │
└──────────────────────────────────────────────┘
```

| Behavior | Specification |
|---|---|
| Entry point | Show Restore only on an Inactive row and only with `Delete Customer`. Never show Edit/Delete on that inactive row. |
| Confirmation | Identify customer name and number, state the result, and offer Cancel and Restore. |
| Success | Set status to Active, record an `EDITED` audit stamp (see assumptions), announce `Customer restored.`, and refresh tabs/counts/list. |
| Failure | Keep the row Inactive and show a persistent actionable error. Never imply success if the server rejects the request. |

## 7. Rights and role variants

Authorization is capability-based, not inferred from role labels. Apply each
right independently to both list actions and entry points. A hidden button is
only a courtesy; server-side authorization is required on every operation.

| Viewer / right | Add customer | Edit active customer | Delete active customer | View inactive / status / stamp | Restore |
|---|---|---|---|---|---|
| Admin or Superadmin, right granted | Show | Show | Show; show blocker if active sales prevent deletion | Show tabs, columns, inactive rows | Show with `Delete Customer` |
| Admin or Superadmin, right absent | Hide | Hide | Hide | Still show Admin/Superadmin status visibility | Hide unless `Delete Customer` is granted |
| User, right granted | Show if `Add Customer` | Show if `Edit Customer` | Show if `Delete Customer`; user sees active rows only | Never show | Never show |
| User, right absent | Hide | Hide | Hide | Never show | Never show |

The table's Actions column is omitted if no applicable action is authorized
for any currently displayed row. Do not leave disabled-looking or decorative
buttons in its place. If a product requirement later calls for disabled
controls, pair each with a visible and programmatically associated explanation;
the current default is to hide unauthorized controls.

## 8. Responsive and accessibility handoff

| Viewport | Layout |
|---|---|
| 1280px and wider | Expanded 256px sidebar; list toolbar and table use available content width. |
| 1024px–1279px | Use the design-system compact navigation behavior; preserve labels through accessible names/tooltips. Table may scroll horizontally. |
| 768px and below | Sidebar becomes a dismissible drawer with visible menu trigger. Toolbar wraps; search remains full-label and usable. |
| 480px and below | Single-column dialog fields; near-full-screen dialogs. Keep table headers and required values accessible through horizontal scrolling rather than hiding them or shrinking text. Ensure touch targets are at least 40px where space permits. |

| Requirement | Acceptance behavior |
|---|---|
| WCAG 2.2 AA contrast | Use approved token pairs; normal text at least 4.5:1 and meaningful boundaries/focus at least 3:1. |
| Status meaning | Always render `Active` or `Inactive` text with the status icon; deleted-row shading is supplementary. |
| Focus | Visible Sprint 1 focus outline on all interactive elements; do not clip it inside scroll containers. |
| Keyboard | Search, tabs, row actions, forms, and dialogs work without a pointer. Tabs expose selected state; dialogs manage and return focus. |
| Screen readers | Label search and form controls; associate inline errors; announce result counts and asynchronous outcomes; use semantic table headers. |
| Reduced motion | Honor the existing reduced-motion preference; do not rely on animation to communicate changes. |

## 9. Products and Price History — S2-UIX-02 consistency notes

These are reference facts only; this ticket does not define the Products or
Price History wireframes.

| Area | Preserve in S2-UIX-02 |
|---|---|
| Products list | Prod Code, Description, Unit, Current Price; Admin/Superadmin add Status and Stamp. Active actions: Prices, Edit, Delete. Inactive rows: Restore. User sees active rows only and no Status/Stamp. |
| Product fields | Unit is a dropdown: `pcs`, `can`, `pair`, `meter`, `box`, `kg`, `liter`. |
| Price History | Per-product dialog; Effective Date and Unit Price, with Admin/Superadmin Status and Stamp; tabs Active / Inactive / All; authorized actions Edit, Delete, and `+ Add Price`. |
| Current price | Derived from the price with the latest effective date that is not in the future. Display it; never make it a typed field. |
| Delete blocking | A product on active sale lines cannot be deleted. Explain the reason and exact count, as for blocked customer deletion. |
| Permissions | Apply Add/Edit/Delete Product and Add/Edit/Delete Price separately; omit controls the viewer lacks and enforce the same rights server-side. |
