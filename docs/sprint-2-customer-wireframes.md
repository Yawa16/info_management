# Hope, Inc. ERP — Sprint 2 Customer Wireframes

**Ticket:** S2-UIX-01 · **Reference viewport:** 1440px desktop

**Wireframe treatment:** Low-fidelity, greyscale structure with real labels. No decorative color or new visual tokens.

These wireframes reuse the Sprint 1
[design system](./hope-erp-design-system.md) and
[style guide](./hope-erp-style-guide.html): 256px desktop sidebar, page/table
layouts, existing inputs/selects/buttons/badges/dialogs, focus ring, spacing,
type, and status/deleted-row treatments. No new colors, sizes, or components
are introduced. Bracketed user/date text is sample audit data, not a real
identity or timestamp.

## Assumptions

| Topic | Decision |
|---|---|
| Cust No | Generated by the system on Add. Do not display it as an input before creation. On Edit, show the value as read-only. |
| Required fields | Customer Name and Pay Terms are required. Address is optional. |
| Status and Stamp | Never typed or edited in Add/Edit. They are read-only list fields shown to Admin/Superadmin only. Soft delete/restore changes status through its action and the server creates the stamp. |
| Rights | Hide unauthorized actions consistently; do not render disabled controls. The server independently checks every operation. Restore uses `Delete Customer` because no separate restore right is specified. |
| User visibility | User-role accounts see Active records only and never see Status, Stamp, status tabs, or Restore. Their row buttons are limited to granted rights. |
| Search | Match Cust No, Customer Name, Address, and Pay Terms, case-insensitively after trimming outer whitespace. Filter as the user types. |
| Status counts | Counts are totals for each status and do not change with a search query. Search results are the intersection of query and selected status. |
| Sort and pagination | Default sort is Cust No ascending; page size defaults to 10. |
| Restore audit | The defined stamp events are CREATED / EDITED / DELETED. With no RESTORED event specified, a successful restore writes an EDITED stamp. |

example actions blindly.

### Layout and list behavior

| Element | Specification |
|---|---|
| Shell | Sprint 1 expanded 256px sidebar; Customers is selected and has `aria-current="page"`. At 1440px, use 32px content gutters and the existing 1200px maximum content width. |
| Heading | `Customers`; supporting copy `Manage customer records and payment terms.` |
| Status tabs | Admin/Superadmin only: `Active {count}`, `Inactive {count}`, `All {count}`. Default selection is Active. Each count is a status total, not a search-result count. |
| Search | Persistent accessible name `Search customers`; placeholder `Customer number, name, address, or payment terms`; accessible clear control `Clear search`. |
| User columns | Cust No, Customer Name, Address, Pay Terms, then Actions only if at least one action is permitted. No Status/Stamp columns. Active rows only. |
| Admin/Superadmin columns | Cust No, Customer Name, Address, Pay Terms, Status, Stamp, Actions. Show status as text (`Active` / `Inactive`) with its existing icon/badge; never rely on color alone. |
| Active-row actions | Show Edit only with `Edit Customer`; show Delete only with `Delete Customer`. |
| Inactive-row actions | Admin/Superadmin only. Show Restore only with `Delete Customer`; do not show Edit or Delete. Shade the row using the existing deleted-row treatment, and retain readable text. |
| Stamp | Read-only `CREATED / EDITED / DELETED · {user} · {localized date/time}`. Show the latest event. Never show a stamp input. |
| Rows | Sample rows use the provided customer IDs, names, and payment terms. Address is `—` because no sample address was provided. |
| Table | Semantic header cells; keep actions visible without hover. On desktop/tablet, allow horizontal scrolling instead of shrinking text or hiding required columns. |
| Count/pagination | Show matching row range and total after current status + search + sort. Pagination behavior is specified in Screen 4. |

### Numbered callouts

1. The Admin/Superadmin status tabs expose Active, Inactive, and All with
   counts. The User sees no tabs and cannot query inactive records.
2. The Add button is visible only with `Add Customer`; role labels do not imply
   this right.
3. Search applies to the selected status. Admin/Superadmin can search Inactive
   or All; User search is restricted to Active records.
4. Status text and its badge distinguish Active from Inactive; the C-004 row
   also has a shaded background and a `DELETED` stamp. Status is never conveyed
   by shading/color alone.
5. Active-row actions are rights-gated. Inactive rows offer Restore only;
   never show Edit/Delete for C-004.
6. If C-004 is restored, refresh the status counts and current list. It appears
   as Active; a User can then see it.
7. Clicking Delete opens the confirmation in the Delete and Restore section.
   If active sales block deletion, show the count and copy from the Delete and
   Restore section instead of offering a confirm action.

### Keyboard, focus, and errors

| Item | Behavior |
|---|---|
| Initial focus | On navigation, place focus on the `Customers` page heading. Do not steal focus on an in-place refresh. |
| Tab order | Add Customer (if allowed) → Admin/Superadmin status tabs → Search → Clear search (when query is non-empty) → sortable headers → row actions in row order → Rows per page → Previous → page numbers → Next. Skip absent controls. |
| Status tabs | Arrow keys move between tabs; Home/End move to first/last; Enter/Space selects. Expose selected state programmatically. |
| Search | Typing keeps focus in the field. Announce the updated result count politely. Escape clears a non-empty query; otherwise it does not navigate away. |
| Dialog entry | Add/Edit opens Screen 2 and focuses Customer Name. Delete/Restore opens its confirmation and focuses Cancel. A blocked-delete dialog focuses its Close button. |
| Validation | List controls have no required-field validation. Search accepts any text. If loading fails, keep the query and selected tab. |
| Load error copy | `We couldn't load customers. Check your connection and try again.` Provide `Try again`; do not render this as an empty list. |
| No records | `No customers yet.` Show `+ Add Customer` only when the viewer has `Add Customer`. |

| Field/control | Add | Edit | Validation and exact error copy |
|---|---|---|---|
| Cust No | Not shown before save; system-generated on successful creation. | Shown as read-only `C-001`; not user-editable. | No validation. |

| Save | Create customer. | Save edits. | Keep dialog and entered values on error; prevent duplicate submission while saving. |

### Numbered callouts

1. Cust No is generated by the system after Add succeeds. On Edit it is
   displayed read-only. It is not a form field users can change.
2. Customer Name and Pay Terms are required; Address is optional. Associate
   each inline error with its input using `aria-describedby` and `aria-invalid`.
3. Pay Terms is a keyboard-operable single-select/drop-down with exactly the
   five options listed above.
4. Status and Stamp are not fields in either dialog. The server creates
   stamps for successful changes; the user never types audit metadata.
5. Save success closes the dialog and announces `Customer added.` or
   `Customer updated.` Edit refreshes the Stamp column from the saved server
   response.
6. On server failure, keep the dialog and values. Show
   `We couldn't save the customer. Try again.` Do not show a success message.
7. If close/cancel is requested after an edit, show
   `Discard your changes? Your edits haven't been saved.` Buttons:
   `Keep editing` and `Discard changes`.

### Keyboard, focus, and validation

| Item | Behavior |
|---|---|
| Focus on open | Focus Customer Name in both Add and Edit. Announce the dialog title and description. |
| Tab order | Customer Name → Address → Pay Terms → Cancel → Save → Close → Customer Name. Cust No is read-only and not in the tab order. Keep Tab/Shift+Tab inside the dialog. |
| Close | Escape follows the same unsaved-changes guard as Cancel/Close. During save, prevent close and duplicate submission. On close, return focus to the control that opened the dialog. |
| Validation timing | Validate required fields on blur. After a field first errors, revalidate it on input/change. On submit, validate all required fields and focus the first invalid field. Address is optional and has no required validation. |
| Error presentation | Place exact field error copy directly below the field and associate it programmatically. Do not rely on a toast or color alone. |
| Pay Terms keyboard | Native/select behavior: open with Enter/Space, move options with arrow keys, commit with Enter, cancel with Escape. |

## Screen 3 — Search behavior and no-results state

```text
ADMIN / SUPERADMIN: status and query are intersected
+-----------------------------------------------------------------------+
| [Active 4] [Inactive 1] [All 5*]                                      |
| Search customers [ acme______________________________ ] [Clear search]|
| Showing 1 of 5 customers in All                                      |
| C-001 | Acme Corporation | — | Net 30 | Active | CREATED · ...       |
+-----------------------------------------------------------------------+

NO MATCHES
+-----------------------------------------------------------------------+
| [Active 4] [Inactive 1] [All 5*]                                      |
| Search customers [ zzz______________________________ ] [Clear search]|
| No customers match "zzz" in All.                                     |
| Change the search or use Clear search to see customers.              |
+-----------------------------------------------------------------------+
```

| Search behavior | Specification |
|---|---|
| As-you-type | Update local results immediately; debounce remote requests by 250ms. Cancel/ignore stale responses so an older query cannot replace newer results. |
| Fields matched | Cust No, Customer Name, Address, Pay Terms. Case-insensitive; trim query whitespace. Do not search audit stamps or action labels. |
| Tab interaction | Admin/Superadmin search intersects the selected tab: Active + query, Inactive + query, or All + query. Changing tabs retains the query. Clearing the query retains the selected tab. |
| User interaction | User has no status tabs; search only the Active records they are allowed to see. |
| Counts | Tab counts remain full status totals while searching. The result count reports the query-and-tab intersection. |
| Clear | `Clear search` clears the query and restores the current tab's full list. Escape in a non-empty search field also clears it. |
| No results | Exact copy: `No customers match "{query}" in {status}.` Supporting copy: `Change the search or clear it to see customers.` Keep the query and selected tab visible. |
| Empty status | If the query is empty and the selected tab has no rows: `No {status} customers.` Do not show the no-search-results copy. |
| Search error | Keep the prior rows, query, and tab. Exact copy: `We couldn't update customer results. Try again.` Provide `Try again`; announce the failure. |

### Numbered callouts

1. Filtering starts as the user types; local feedback is immediate and remote
   search is debounced 250ms.
2. The query matches customer number, name, address, and payment terms. A
   clear control appears only when there is a query.
3. Status tabs are independent filters that combine with search, not
   replacements for it. Changing a tab keeps the query; clearing search keeps
   the tab.
4. Counts on tabs are unchanged by search. `Showing {n} of {total}` describes
   the filtered result and current tab.
5. No results is distinct from an empty dataset/status. Provide an explicit
   Clear search action without silently resetting the user's tab.

### Keyboard, focus, and validation

| Item | Behavior |
|---|---|
| Initial focus | On the list, focus remains on the current control. A fresh route focuses the Customers heading as specified in Screen 1. |
| Tab order | Add Customer (if allowed) → Admin/Superadmin status tabs → Search → Clear search (when shown) → sortable headers and row actions when results exist. User: Add Customer (if allowed) → Search → sortable headers and row actions when results exist. |
| Validation | No search text is invalid; filtering does not require submission. |
| Feedback focus | Keep focus in Search through updates; announce counts/errors via a polite live region. Do not move focus into the result rows. |
| Error copy | `We couldn't update customer results. Try again.` Preserve entered query and selected status. |

## Screen 4 — Sorting and pagination

This is an illustrative long-list state with 27 records: 24 Active and 3
Inactive. The counts differ from the five sample rows above to show pagination.

```text
+----------------------------------------------------------------------------------------------------+
| Customers                                                         [+ Add Customer]                |
| [Active 24] [Inactive 3] [All 27*]  [Search customers...] [Clear search]                          |
|                                                                                                    |
| Cust No ^ | Customer Name ↕ | Address ↕ | Pay Terms ↕ | Status ↕ | Stamp ↕ | Actions               |
|-----------|-----------------|-----------|-------------|----------|---------|----------------------|
| C-001     | Acme Corporation| —         | Net 30      | Active   | CREATED | [Edit] [Delete]      |
| ...                                                                                               |
|                                                                                                    |
| Showing 1 to 10 of 27 customers     Rows per page [10 v]     [Previous] [1] [2] [3] [Next]       |
+----------------------------------------------------------------------------------------------------+
```

| Behavior | Specification |
|---|---|
| Default sort | Cust No ascending. Header shows `Cust No` and an ascending indicator; header exposes `aria-sort="ascending"`. |
| Sortable fields | Cust No, Customer Name, Address, Pay Terms, and (Admin/Superadmin only) Status and Stamp. Actions is not sortable. User never gets Status/Stamp sort controls. |
| Sort direction | Activate a column header to sort ascending; activate it again to reverse. Switching columns starts ascending. Strings sort A–Z; Status order is Active then Inactive; Stamp sorts chronologically. Expose direction in text/icon and `aria-sort`, not color alone. |
| Pagination | Choose pagination, not load-more. Default 10 rows per page; options 10, 25, 50. Show `Showing {first} to {last} of {total}`, Previous, numbered pages, and Next. |
| Page changes | Keep status and search. Changing status, query, sort column/direction, or page size returns to page 1. After an action, refresh totals and remain on the current page if it still exists; otherwise move to the last available page. |
| No rows | Hide page numbers and show the applicable empty/no-results state from Screens 1 and 3. |

### Numbered callouts

1. The current sort starts at Cust No ascending. Every sortable header has a
   visible direction cue and correct `aria-sort`.
2. Sort order applies to the current status/search result set. It does not
   clear the tab or query.
3. Pagination covers only the filtered/sorted result set. The summary uses
   that set's total, not the unfiltered database total.
4. A filter/search/sort/page-size change returns to page 1 so the user does
   not land on a stale or empty later page.
5. Previous and Next are unavailable at their respective boundaries and
   expose disabled semantics; numbered page buttons expose the current page.

### Keyboard, focus, and validation

| Item | Behavior |
|---|---|
| Tab order | Add Customer (if allowed) → status tabs (Admin/Superadmin) → Search → Clear search (when shown) → sortable headers in visual order → row actions in row order → Rows per page → Previous → numbered pages → Next. |
| Sorting | Enter/Space activates a header button. Preserve focus on that header after sort and announce the new sort order politely. |
| Pagination | Enter/Space activates a page control. After page change, focus the page heading `Customers` and announce the new range; do not leave focus on a removed page button. |
| Focus on dialog | No dialog is opened by sort/page controls. Row actions that open Add/Edit/Delete/Restore follow Screen 2 or the confirmation behavior in Screen 1. |
| Validation | Sort and pagination have no required-field validation. Rows-per-page is a labeled select limited to 10, 25, 50. |
| Error copy | If a page/sort request fails: `We couldn't update customer results. Try again.` Keep the prior rows, filters, and sort; offer Retry. |

## Control-to-right mapping

Use one rule consistently: **hide the control when the required right is
missing**. Do not render a disabled-looking action without an explicit product
requirement. Every hidden control remains protected by server-side checks.

| Control | Right / visibility rule | What User sees when right is missing |
|---|---|---|
| `+ Add Customer` | `Add Customer` | Hidden; no entry point to Add dialog. |
| Edit row action / Edit dialog entry point | `Edit Customer` | Hidden; data fields are not editable. Other independently granted actions remain available. |
| Delete row action / Delete confirmation entry point | `Delete Customer` | Hidden; no delete dialog. |
| Restore row action | `Delete Customer` (assumption; no separate Restore right supplied) and Admin/Superadmin view | Hidden. User never sees inactive rows or Restore, even if granted Delete Customer. |
| Status tabs | Admin/Superadmin role visibility, not a CRUD right | Hidden for User; User sees Active list only. |
| Status and Stamp columns/values | Admin/Superadmin role visibility, not a CRUD right | Not rendered. |
| Search, sort, pagination, list navigation | No customer CRUD right; available for records the role may view | Available. Search remains limited to Active rows for User. |
| Add/Edit form fields | Gate the entire form by `Add Customer` / `Edit Customer`; no separate field rights | No dialog if the matching right is missing. In Edit, Cust No is read-only for authorized editors. |
| Delete/Restore submit | `Delete Customer`, enforced again by the server | Hidden entry point; if a stale request is rejected, retain the record and show an error without claiming success. |

```text
| and can be restored by an authorized |  | those sales before deleting this     |
| administrator.                       |  | customer.                            |
|                                      |  |                                      |
|        [Cancel] [Delete customer]    |  |                               [Close]|
+--------------------------------------+  +--------------------------------------+

RESTORE
+--------------------------------------+
| Restore customer?             [Close]|
| Restore Umbrella Corp (C-004) to     |
| Active? It will appear in active     |
| customer lists.                     |
|                                      |
|               [Cancel] [Restore]    |
+--------------------------------------+
```

| State | Wireframe copy and behavior |
|---|---|
| Delete allowed | Title `Delete customer?`; message `Delete {Customer Name} ({Cust No})? The customer will become inactive and can be restored by an authorized administrator.` Buttons `Cancel` and `Delete customer`. |
| Delete blocked | Title `Customer can't be deleted`; for one: `{Customer Name} ({Cust No}) has 1 active sale. Close or cancel that sale before deleting this customer.` For multiple: `{Customer Name} ({Cust No}) has {count} active sales. Close or cancel those sales before deleting this customer.` Show exact server count and `Close` only; no destructive action. |
| Delete failed | `We couldn't delete this customer. Try again.` Keep the record Active; show Retry where safe. |
| Restore | Title `Restore customer?`; message `Restore {Customer Name} ({Cust No}) to Active? It will appear in active customer lists.` Buttons `Cancel` and `Restore`. |
| Restore failed | `We couldn't restore this customer. Try again.` Keep the record Inactive; do not announce success. |
| Success | Delete: `Customer moved to Inactive.` Restore: `Customer restored.` Announce politely and refresh rows/counts. |

### Numbered callouts and keyboard behavior

1. The allowed Delete dialog identifies the customer by name and Cust No,
   explains that deletion is soft, and says it can be restored.
2. The blocked state shows the server's exact active-sales count and offers
   Close only; it never offers a Delete/confirm action.
3. Restore identifies the Inactive customer and states that it will appear in
   Active lists.
4. Open confirmation dialogs with focus on Cancel. Tab order is Cancel →
   Delete/Restore → Close; Escape closes without submitting and returns focus
   to the row action.
5. The blocked-delete dialog has one Close action. Focus it on open; closing
   returns focus to the row's Delete trigger.
6. During submission, keep focus in the dialog and prevent duplicate actions.
   On success, close and announce the result; on failure, retain context and
   show the exact error copy in the table above.
