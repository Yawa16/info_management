# Hope, Inc. ERP — Sprint 2 Product and Price History Wireframes

**Ticket:** S2-UIX-02 · **Reference viewport:** 1440px desktop

**Wireframe treatment:** Low-fidelity, greyscale structure with real labels. No decorative color or new visual tokens.

These wireframes reuse the Sprint 1
[design system](./hope-erp-design-system.md), [style guide](./hope-erp-style-guide.html),
and [S2-UIX-01 customer patterns](./sprint-2-customer-wireframes.md): existing
tables, cards, inputs, selects, dialogs, status treatments, focus rings,
spacing, and typography. Do not introduce new colors, sizes, or components.

## Assumptions

| Topic | Decision |
|---|---|
| Product code | Generated by the system on Add; shown read-only on Edit. The generation rule was not supplied. |
| Required product fields | Description and Unit are required. The provided units are `pcs`, `can`, `pair`, `meter`, `box`, `kg`, and `liter`. |
| Current Price | Calculated from the latest **Active** price whose effective date is today or earlier. Future and Inactive prices do not determine today's current price. Never show it as an editable product field. |
| Price examples | The dated P-003 rows below are illustrative. This example uses 11/19/2026 as today so the current and future states are unambiguous. Replace sample dates/prices with actual seed data. |
| Future-price hint | Recommend showing `Next price from {date}` in the product list only when a future Active price exists. It explains why the current price differs from an upcoming scheduled price without making the list look as if the future price applies today. |
| Empty price | A product with no Active price effective today shows `—` in the list and the explicit `No price yet` state in Price History. Do not display `$0.00`. |
| Price history roles | Admin/Superadmin see Active / Inactive / All tabs, Status, and Stamp. User sees Active prices only and no tabs, Status, or Stamp, following S2-UIX-01. |
| Rights | Hide unauthorized actions; independently enforce each operation on the server. `Restore` uses the matching Delete right because no separate Restore right is specified. |
| Price history access | `Prices` opens history for a user allowed to view the product. No separate View Price right was specified; Add/Edit/Delete controls are gated individually. |
| Inactive price | Inactive means soft-deleted. Restore returns that price row to Active. Only an authorized Admin/Superadmin can see inactive rows. |
| Past effective date | Allow backdating but show a non-blocking warning because it can change today's calculated price. |
| Currency | Show a dollar prefix, exactly two decimal places, and reject negative values. A value of `$0.00` is permitted unless the business rule says otherwise. |

### Layout and list behavior

| Element | Specification |
|---|---|
| Shell | Reuse the expanded 256px Sprint 1 sidebar, with Products selected and `aria-current="page"`. Use the 1440px desktop content width and gutters from the design system. |
| Heading | `Products`; supporting copy `Manage products and their prices.` |
| Status tabs | Admin/Superadmin only: `Active {count}`, `Inactive {count}`, `All {count}`. Default selection is Active; counts are status totals, not search-result counts. |
| Admin/Superadmin columns | Prod Code, Description, Unit, Current Price, Status, Stamp, Actions. Status is visible text plus the existing badge/icon. |
| User columns | Prod Code, Description, Unit, Current Price, Actions. Active rows only; no Status or Stamp. Omit Actions if no action is permitted. |
| Current Price | Latest Active effective date on or before today. Align the amount consistently and display exactly two decimals. For no applicable price, show `—` with accessible name `No price yet`. |
| Future-price hint | For a product with a future Active row, show secondary text `Next price from {mm/dd/yyyy}` beside/below today's current price. Keep the current amount first and visually primary. Do not show the hint if no future Active row exists. |
| Inactive product | Admin/Superadmin only; use the existing shaded deleted-row treatment, `Inactive` text, `DELETED` stamp, and `Restore` action. User never sees the row. |
| Active-row actions | `Prices` is available to viewers of the product. `Edit` requires `Edit Product`; `Delete` requires `Delete Product`. |
| Product deletion | If an active sale line blocks deletion, show the authoritative count and exact blocked state described in the S2-UIX-01 delete pattern. Never present a successful delete state when blocked. |
| Search, sort, pagination | Reuse S2-UIX-01 Screen 3 and Screen 4 behavior, adapting searchable fields to Prod Code, Description, Unit, and Current Price. Do not search audit stamps or action labels. |
| Product sample rows | Use P-001 through P-005 and the product values from the Sprint 2 brief. P-004 has no price; P-005's future schedule is illustrative until actual price data is supplied. |

### Numbered callouts

1. Admin/Superadmin can filter by Active, Inactive, or All; User sees only
   active rows and no status controls.
2. The Current Price column is a calculated read-only amount. `—` means no
   Active price is effective today; it never means zero.
3. If a scheduled future Active price exists, the optional `Next price from
   {date}` hint appears after today's amount. It is not the current price.
4. P-004 is shaded and explicitly labeled Inactive, with Restore; the row is
   not hidden from an authorized Admin/Superadmin.
5. `Prices`, Edit, Delete, and Restore are shown according to the rights
   table. A role label does not grant a right by itself.
6. Add Product appears only with `Add Product`. A user with no product-add
   right has no Add entry point.

### Keyboard, focus, and errors

| Item | Behavior |
|---|---|
| Initial focus | On route navigation, focus the `Products` heading. Do not move focus on an in-place refresh. |
| Tab order | Add Product (if allowed) → Admin/Superadmin status tabs → Search → Clear search (when present) → sortable headers → row actions in row order → pagination controls. Skip hidden controls. |
| Status tabs | Arrow keys move between tabs; Home/End move to first/last; Enter/Space selects. Expose selected state programmatically. |
| Row actions | Use visible text labels, not icon-only actions. Accessible names identify the product, e.g. `Open prices for Lubricant Oil 5L` or `Edit Safety Gloves XL`. |
| Dialog entry | Add/Edit Product focuses Description. Price History focuses its heading. Add/Edit Price focuses Effective date. Destructive confirmation focuses Cancel. |
| Search/list validation | No required-field validation. Announce result count politely and preserve query/filter/sort if a request fails. |
| Load error | `We couldn't load products. Check your connection and try again.` Provide `Try again`; do not render a load failure as an empty list. |

### Numbered callouts

1. Product code is assigned by the system; never invite users to type or
   change it.
2. Description and Unit are required. Unit options are limited to the seven
   supplied values.
3. Current Price is not part of product creation/editing. The helper directs
   users to the separate Prices workflow.
4. On success, close and announce `Product added.` or `Product updated.`
   Refresh the list and audit Stamp from the server response.
5. On save failure, retain values and show
   `We couldn't save the product. Try again.` Do not show a success message.

### Keyboard, focus, and validation

| Item | Behavior |
|---|---|
| Focus on open | Focus Description and announce the dialog title/description. |
| Tab order | Description → Unit → Cancel → Save → Close → Description. Product Code is read-only and not in the tab order. Keep Tab/Shift+Tab inside the dialog. |

| Error presentation | Show exact copy under the field, associate it with `aria-describedby`, and set `aria-invalid`. Do not rely on color or toast alone. |
| Close behavior | Escape follows the same unsaved-changes guard as Cancel/Close. During save, prevent close and duplicate submission. On close, return focus to the opener. |

### Numbered callouts

1. The dialog title identifies both product description and code, preventing
   price changes on the wrong product.
2. Admin/Superadmin can select Active, Inactive, or All. User sees Active

3. The Active row effective 10/01/2026 is today's current price in this
   illustrative scenario. The icon plus `CURRENT PRICE TODAY` label explains
   its state without color.
4. The 12/15/2026 row is scheduled for a future date. It is visibly distinct
   and does not replace the current price until its date becomes effective.
5. The 07/01/2026 inactive row is shaded and labeled; Restore requires
   `Delete Price`. Do not show Edit/Delete on inactive rows.
6. A tab or action hidden for a missing right is not replaced with a disabled
   control. Every mutation is re-authorized server-side.

Use a date-only value (not a timezone-shifting timestamp), a keyboard-operable

requested `mm/dd/yyyy` format in the field hint. The price is always scoped to
the product named in the dialog.

| Field/state | Behavior | Exact copy |
|---|---|---|
| Effective date, empty | Required; validate on blur and submit. | `Enter an effective date.` |
| Effective date, malformed/impossible | Require a valid calendar date in `mm/dd/yyyy`. | `Enter a valid date in mm/dd/yyyy format.` |
| Past-date warning | Non-blocking warning when the date is before today. It may change today's calculated price; allow Save after the warning is read. | `This date is in the past. Saving it may change today's current price.` |
| Duplicate date | One price per product/effective date. On Edit, exclude the row being edited from the duplicate check. | `A price already exists for this effective date.` |
| Unit price, empty | Required. | `Enter a unit price.` |
| Negative price | Reject any amount below zero. | `Enter a price of $0.00 or more.` |
| Non-numeric price | Reject letters, invalid separators, and malformed values. | `Enter a valid amount, such as 28.00.` |
| More than 2 decimals | Do not silently round. | `Enter no more than 2 decimal places.` |
| Zero | Accept `$0.00` under the current assumption; confirm business policy before implementation. | No error. |
| Save failure | Keep entered date and amount. | `We couldn't save this price. Try again.` |
| Success | Close, refresh history/product list, and announce the result. | `Price added.` / `Price updated.` |

### Numbered callouts

1. The product identity stays visible above the form; the price cannot be
   accidentally attached to a different product.
2. Effective date is a required date-only value with explicit `mm/dd/yyyy`
   format. Do not let timezone conversion shift the selected calendar day.
3. A past date raises a visible, non-blocking warning. It is not an error and
   does not prevent backdated corrections.
4. The server enforces one price per product/effective date, including during
   concurrent edits. On a conflict, keep the form open and show the duplicate
   date copy.
5. Currency is stored/displayed with two decimals, has no negative values,
   and is never silently rounded from extra precision.
6. On validation failure, associate field copy with the control, mark
   `aria-invalid`, preserve values, and focus the first invalid field on
   submit.

### Keyboard, focus, and validation

| Item | Behavior |
|---|---|
| Focus on open | Focus Effective date. Announce Add/Edit Price and the product identity. |
| Tab order | Effective date input → date-picker trigger → Unit price → Cancel → Save Price → Close → Effective date. Keep Tab/Shift+Tab inside. |
| Date picker | Arrow keys navigate calendar dates; Page Up/Down changes month; Enter selects; Escape closes the calendar and returns focus to its trigger. Provide an accessible month/year heading and weekday labels. |
| Currency entry | Keep focus in the field; announce the currency prefix/format. On blur, normalize valid input to two decimals without changing its numeric value. |
| Validation timing | Validate on blur; after first error, revalidate on input/change. On submit validate all fields and focus the first invalid one. Display the past-date warning after the date is recognized and again before save if the value changed. |
| Duplicate check | Check on blur and submit; server response is authoritative. Never clear the date or amount on a conflict. |
| Warning announcement | Expose the past-date warning as an associated description/alert; do not require color to identify it. |
| Close behavior | Escape uses the same unsaved-changes guard as Cancel/Close. During save, prevent duplicate submission and closing. Return focus to the opening Add/Edit action. |

| Item | Behavior |
|---|---|
| Product cards | Tab order: menu trigger → Add Product (if allowed) → status tabs (Admin only) → Search → sort controls → card actions in visual order → pagination. |
| History cards | Tab order: tabs (Admin only) → Add Price (if allowed) → row actions in date order → Close. Omit unauthorized and User-hidden controls. |
| Sheets | Focus title/first field on open, keep focus within the sheet, support Escape subject to unsaved-change/save guards, and return focus to the opener on close. |
| Date picker | Keep the calendar within the viewport, allow scrolling if needed, and preserve the same keyboard behavior and `mm/dd/yyyy` format as Screen 4. |
| Validation | Use the exact field errors from Screen 4; place errors next to fields and scroll the first invalid field into view without obscuring it under the sheet header/footer. |
| Narrow-screen errors | Keep the same error text and retry action as desktop. Allow wrapping; never clip or communicate an error by color alone. |

## Control-to-right mapping

Use one rule consistently: **hide an action when its required right is
missing**. User-role accounts see only Active data and no Status/Stamp. Server
authorization independently protects every mutation.

| Control | Required right / visibility rule | What User sees when the right is missing |
|---|---|---|
| `+ Add Product` | `Add Product` | Hidden; no Add Product entry point. |
| Product Edit | `Edit Product` | Hidden; product values remain view-only. |
| Product Delete | `Delete Product` | Hidden; no delete confirmation entry point. |
| Product Restore | `Delete Product` (assumption; no separate Restore right supplied) and Admin/Superadmin visibility | Hidden. User never sees Inactive products or Restore. |
| `Prices` entry point | Product-view access; no separate View Price right is specified | If the product itself is not visible, its Prices action and history are also unavailable. |
| `+ Add Price` | `Add Price` | Hidden; history remains viewable if product access permits. |
| Price Edit | `Edit Price` | Hidden; that row is not editable. |
| Price Delete | `Delete Price` | Hidden; no delete confirmation entry point. |
| Price Restore | `Delete Price` (assumption; no separate Restore right supplied) and Admin/Superadmin visibility | Hidden. User never sees Inactive prices or Restore. |
| Status tabs | Admin/Superadmin role visibility, not a CRUD right | Hidden; User sees Active records only. |
| Status and Stamp | Admin/Superadmin role visibility, not a CRUD right | Not rendered. |
| Current Price / Price History values | Product-view access | Available as read-only product data; never editable through product form. |
| Product form | Gate entire Add/Edit form by `Add Product` / `Edit Product` | No dialog if matching right is missing. |
| Price form | Gate Add/Edit form by `Add Price` / `Edit Price` | No dialog if matching right is missing. |
| Mutation submit | Matching Product/Price right; server rechecks authorization | On stale/denied requests, retain form and show a permission error without claiming success. |

## Delete and restore confirmations

| Action | Copy and behavior |
|---|---|
| Delete product, allowed | Title `Delete product?`; message `Delete {Description} ({Prod Code})? The product will become inactive and can be restored by an authorized administrator.` Buttons `Cancel` and `Delete product`. |
| Delete product, blocked | Title `Product can't be deleted`; message `{Description} ({Prod Code}) is used by {count} active sale lines. Close or cancel those lines before deleting this product.` Show the authoritative count and `Close` only. |
| Delete product, failed | `We couldn't delete this product. Try again.` Keep it Active; offer Retry where safe. |
| Restore product | Title `Restore product?`; message `Restore {Description} ({Prod Code}) to Active? It will appear in active product lists.` Buttons `Cancel` and `Restore`. |
| Delete price | Title `Delete price?`; message `Make the price effective {date} for {Prod Code} inactive?` Buttons `Cancel` and `Delete price`. Recompute Current Price after success. |
| Restore price | Title `Restore price?`; message `Restore the price effective {date} for {Prod Code} to Active?` Buttons `Cancel` and `Restore`. If another Active price has the same effective date, block and explain the conflict. |
| Price mutation failure | `We couldn't update this price. Try again.` Retain the existing state; do not report success. |
| Confirmation focus | Focus Cancel on open; Tab proceeds to destructive/restore action then Close. Escape cancels and returns focus to the row action. During submission prevent duplicate actions. |

## Open UX questions or risks

| Item | Risk / assumption to confirm |
|---|---|
| Product code | The prompt lists Prod Code but not whether it is generated or manually assigned. This handoff assumes system generation and read-only display on Edit. |
| Current price definition | This handoff excludes Inactive prices from Current Price calculation. Confirm that only Active rows participate, as the source rule says latest non-future date but does not explicitly mention status. |
| Future price examples | No future prices or effective dates were supplied. P-003/P-005 future rows above are illustrative only; replace them with actual sample data if available. |
| Zero price | `$0.00` is accepted because the requirement forbids negatives but does not forbid zero. Confirm whether zero is a valid business price. |
| Past date edits | Backdating can immediately change today's current price. Confirm whether a warning is enough or an additional confirmation is required. |
| Duplicate effective dates | The form assumes one price per product/date. Confirm this matches database constraints and define whether inactive rows also block a duplicate until restored/removed. |
| Restore conflicts | Restoring an Inactive row may conflict with an Active row on the same effective date. Server behavior and user-facing resolution need confirmation. |
| Product/price permissions | `Prices` visibility and read access are not represented by a separate right. This handoff assumes product viewers may open read-only history; confirm policy. |
| Restore authorization | Restore maps to the matching Delete right because no separate restore permission was provided. Confirm before implementation if permission policy differs. |
| Price history status/stamp | The prompt calls for Status and Stamp on the Admin view but does not specify their exact format. This handoff reuses the S2-UIX-01 `CREATED / EDITED / DELETED · user · date/time` format. |
| Sale-line delete block | The server must return an authoritative active sale-line count. The UI cannot infer or cache whether a product is deletable. |
